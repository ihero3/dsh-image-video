# 性能基线（Track A）

> 目的：给"规模化"一个**可复现的数字**，而不是靠感觉。跑法：`pnpm exec vitest run tests/store-scale.test.ts`（真实数字会打印在 `[scale]` 前缀行）。

## 存储（A8）：一万素材 / 20 项目

| 指标 | 实测（Mac mini, 2026-10-18） | 预算（防抖动 ~10×） |
| --- | --- | --- |
| 文档大小 | **1.64 MB** | — |
| 冷加载（parse + 迁移 + 归一化） | **11.7 ms** | < 3000 ms |
| `listAssets(projectId)` 首次（建索引） | **0.0 ms** | < 300 ms |
| `listAssets(projectId)` 后续均值 | **0.00 ms** | < 50 ms |
| 追加素材并落盘（全量重写 1.64 MB） | **12.5 ms** | < 3000 ms |

**结论**：单 JSON + 原子写（tmp→rename）+ `.bak` 镜像 + 朴素全表读，在 **1 万素材量级完全够用**，**不需要**在 V1 引入 SQLite/分片（引入会带来迁移与并发复杂度，收益不成立）。
**什么时候需要重估**：素材量级到 **5 万以上**，或单次落盘 > 100 ms、冷加载 > 300 ms 时，再评估分片/嵌入式库。

## 已内置的规模化措施

- **写合并**：内容未变化时跳过落盘（轮询/重复保存很常见）→ `writeCount` 可观测真实写次数
- **读路径保持朴素**：实测 1 万素材下 `listAssets` 全表 filter+sort 已在毫秒级 → **不加索引**（多加一层缓存反而引入失效风险，A8 里已试过并撤销）
- **有界账本**：任务 1000 条上限、使用记录 2000、运行记录 50/项目、节点缓存 200
- **迁移友好**：schemaVersion v2 + 迁移链（只升不降）

## 渲染（A1/A2/A4）

- 导出为异步任务：`RenderRegistry` 默认同时只跑 1 个（`maxConcurrent`），超出排队（`queued`/`queuePosition` 可见）
- 节点级超时护栏：图像 180s / 视频 900s / 其它 120s（工具无视取消也能结束）
